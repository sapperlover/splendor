# 双人《璀璨宝石》对战 AI：实施工作大纲

本文面向后续负责代码实现的 AI agent，确定从对局引擎到训练、评测的完整路线。工程组织保持简单，优先完成可复现、可训练、可验证棋力的闭环。

**确定的主方案：Python 规则引擎 + 分阶段合法动作 + 共享物件编码与集合聚合（Deep Sets）的小型 Actor–Critic + PPO + 历史对手池自我对弈。** 按 4060 Ti 的 8 GB 显存预算设计，16 GB 版本沿用相同方案。第一版完成无搜索策略；信息集采样搜索作为可独立评估的后续增强。

## 1. 目标、范围与规则依据

- 只实现基础版的 **2 人模式**，不是《璀璨宝石：对决》。不为 3–4 人、扩展规则或联网服务预留复杂框架。
- 直接以本地[规则说明](splendor_standard_rules_zh-CN.md)、[发展卡](../data/splendor_cards.csv)、[贵族](../data/splendor_nobles.csv)、[配置](../data/splendor_config.json)为唯一规则及数值来源，不重新考证规则。
- 两人配置：普通宝石每色 4 枚、黄金 5 枚、场上贵族 3 块；其余依本地规则执行。
- 最终交付：完整引擎、随机与启发式对手、训练程序、可恢复的模型检查点、独立评测程序、命令行人机对局及实验报告。图形界面不作为第一版目标。
- 棋力目标先定为稳定击败随机策略和有竞争力的启发式策略，并能通过历史模型对比验证进步；不预先承诺达到人类高手水平或博弈均衡。

## 2. 对局引擎整体架构

采用**单机、内存中的状态机**。规则引擎独立于 PyTorch，训练与人机对局复用同一个引擎。

| 层次 | 主要职责 | 设计边界 |
|---|---|---|
| 静态数据 | 读取卡表、贵族表和常量 | 保留稳定 ID，不在程序内重抄卡牌数值 |
| 完整对局状态 | 牌堆顺序、市场、双方资产、保留牌、当前阶段、先手、终局标记 | 只有引擎和调试回放可以访问全部信息 |
| 规则状态机 | 枚举合法选择、验证并执行动作、补牌、结算与胜负判定 | 所有规则只实现一次，AI 不自行实现另一套规则 |
| 玩家观察 | 从完整状态生成某一玩家有权知道的信息 | 策略网络、价值网络、启发式对手统一使用此入口 |
| 对战与训练适配 | 调用玩家策略、推进对手回合、形成训练样本、记录结果 | 训练截断不改变正式游戏规则 |

引擎需要具备以下能力，具体类名和目录由实现 agent 决定：

- 按种子创建对局，并允许指定首玩家；同一初始条件和动作序列可以重放。
- 获取指定玩家的观察、当前决策者和当前合法候选动作；应用动作后推进到下一个需要选择的阶段或终局。
- 保存和恢复对局，包括随机数状态、待处理购买及回合阶段。游戏随机性、策略采样、对手抽样使用各自的随机源。
- 记录结构化动作日志；完整调试日志不得进入模型输入或直接展示为玩家视角日志。

分数、加成、已购卡数量以持有的卡牌和贵族为准。可以缓存，但必须能够重新计算并检查一致性。普通回合结束时检查 token 上限；执行拿取后的临时状态可以超过上限。

## 3. 动作空间：拆开选择，保留完整规则

不把“主行动 × 支付 × 归还 × 贵族”展开成一个巨大的动作表。一个真实回合内部可以产生多个 AI 决策，但这些决策仍属于同一玩家、同一个回合。

| 决策阶段 | AI 选择 | 处理方式 |
|---|---|---|
| 主行动 | 拿不同色、拿同色、保留公开牌、盲保留某等级、购买公开牌或自己的保留牌 | 枚举全部合法主行动；购买先确定目标牌 |
| 支付 | 五色 token 与黄金的合法支付组合 | 仅购买时进入；选定支付后才实际扣款、购卡及补市场 |
| 归还 | 超过 10 枚时，归还的六色 token 数量向量 | 枚举所有恰好归还超额数量的组合，包括黄金和刚拿的 token |
| 贵族 | 当前满足条件的某一块贵族 | 有符合条件者必须取得一块；取得后执行终局检查 |

不存在选择的阶段自动跳过；只有一个合法选择时可自动执行，并在日志中保留。不能通过自动执行替玩家决定存在多个合法后继状态的选择。唯一例外是 `MAIN_ACTION` 真正没有候选时的正式 forced skip：它是引擎事件，不是策略选择。

关键约束：

- 不同色拿取遵守“有至少三色就必须拿三色，只有一至两色则拿所有非空普通颜色”的本地规则；没有普通颜色可拿时，此行动不可选。同色拿两枚检查拿取前供应量。
- 折后需求为 `need[c] = max(0, cost[c] - bonus[c])`。支付可以枚举黄金分配向量 `g[c]`：满足 `0 ≤ g[c] ≤ need[c]`、`need[c] - g[c] ≤ held[c]`、`Σg[c] ≤ held_gold`；普通色支付为 `need[c] - g[c]`。只有存在合法支付的牌才能成为购买候选。**不能固定成先花普通色、最后花黄金。**
- 不同黄金用途若对应完全相同的实际支付及后继状态，只保留一个候选；不同实际支付不得合并。
- 保留公开牌后立即补市场；盲保留只抽指定等级顶牌。供应有黄金时必须拿取，之后再判断是否归还 token。
- 贵族结算适用于每个回合，不能只在购买后检查；同回合最多取得一块。
- 终局必须计入贵族后检查，并让双方完成相同回合数。先手触发时后手还有一次回合，后手触发时本轮已经结束。
- 平分时比较已购发展卡数量，较少者胜；仍相同为平局。没有玩家可选的 `pass`。`MAIN_ACTION` 无任何合法候选时由引擎强制跳过本回合；任意正常主行动清零连续计数，双方连续各跳过一次则立即平局。forced skip 不产生 `DecisionRequest`。

这使每次选择保持较小：主行动候选少于 50 个；黄金总共只有 5 枚，支付组合最多 252 个；合法回合最多超额 3 枚 token，归还组合最多 56 个；贵族最多 3 个。候选上限来自规则，不通过删减合法策略控制规模。

## 4. 模型观察与信息隔离

统一从“自己 / 对手”的相对视角编码，双方共用一个模型。保留“自己是否先手”“当前阶段”“最后一轮标记”等信息，避免相同表面局面因行动顺序不同而被混淆。

输入包括：

- 公共供应的六色数量、三个等级的剩余牌堆数量。
- 三个等级各自的市场卡牌集合：等级、加成色、分值、五色费用和有效位。同等级最多 4 张，集合内部没有第 1～4 槽的策略含义。
- 最多 3 个贵族组成的集合，包含要求、分值和有效位。
- 双方 token、五色加成、分数、已购卡数量、贵族数量；另用 90 位 `public_purchased` 标记双方已经购买、公开展示的发展卡。每一位只表示对应卡是否已购，不表示是否还在真实牌堆中。
- 自己最多 3 张保留牌的属性；对方最多 3 张保留牌的已知属性、等级、来源和已知/未知标记。
- 待支付的目标牌、需要归还的数量等阶段上下文，以及回合与终局信息。
- 少量可直接计算的辅助特征：可见购卡目标的折后需求和缺口、双方到各贵族的加成缺口；这些特征跟随对应物件一起编码，不能按槽位单独展平而重新引入顺序依赖。不输入人工指定的“最佳行动”。

数值按规则常量作固定缩放，颜色与阶段用 one-hot 编码。空位和未知牌必须可区分；有可能超过缩放基准的分数、加成不能被错误截断。

**信息隔离是训练正确性的要求：**

- 对手从市场保留过的牌持续公开已知；不能在它进入保留区后遗忘身份。
- 对手盲保留牌只暴露允许知道的等级、数量和来源，不暴露费用、分值、加成或真实 ID。
- **对手盲保留时，90 位 `public_purchased` 完全不变。** 只有该牌随后被购买并公开，才将对应位置设为 1；保留公开牌也不设置已购位。禁止通过扫描真实牌堆、取真实剩余卡集合的补集，或使用真实移出牌掩码来构造该特征。
- 牌堆数量减少、对手未知保留牌数量增加属于公开信息；“具体哪一张牌被移出牌堆”仍然未知。任何候选牌概率或记牌辅助特征，只能根据该观察者已知的卡牌身份计算，不能排除对手实际持有但未公开的牌。
- 不输入牌堆顺序、未来补牌、随机种子或随机数内部状态；价值网络也遵守同一限制。
- 候选动作特征只能使用当前已知信息。盲保留候选只表示等级，不能附带将抽到的牌；不能用真实未来补牌计算动作特征。
- 槽位排列和候选排序不得依赖隐藏 ID。隐藏信息不同、玩家已知信息相同的两个状态，应产生相同观察及相同合法候选编码。

第一版使用当前观察和上述明确保存的公开信息，不推断完整隐藏状态，也不使用 RNN 记忆全部历史。这是控制实现和训练成本的取舍；模型不会获得完整的对手行为历史推理能力。

## 5. 模型种类与结构

### 5.1 共享编码器与集合聚合

选择 **PPO 的 Actor–Critic 模型**：Actor 给动作评分，Critic 估计当前玩家的期望回报。PPO 使用采样数据进行有限轮次的小批量更新，适合作为这一轻量方案的起点；本项目的网络规模和训练参数需由实验确认。[PPO 原始论文](https://arxiv.org/abs/1707.06347)

| 部分 | 第一版结构 | 输出 |
|---|---|---|
| 卡牌编码器 | 单张牌属性及合法辅助特征 → 全连接 64 → ReLU → 全连接 64 → ReLU；所有发展卡共享参数 | 每张牌的 64 维向量 `e_card` |
| 贵族编码器 | 单个贵族属性及缺口 → 全连接 32 → ReLU → 全连接 32 → ReLU；所有贵族共享参数 | 每个贵族的 32 维向量 |
| 集合聚合 | 分别聚合三个等级市场、自己的保留牌、对方保留牌、贵族；使用带有效位的求和与有效数量 | 各集合的顺序无关摘要 |
| 状态编码器 | 拼接各集合摘要、公共已购标记、双方资产与阶段上下文 → 全连接 256 → ReLU → 全连接 256 → ReLU | 状态向量 `h` |
| 动作特征 | 动作类型、目标卡/贵族的共享编码、来源/等级、拿取/支付/归还向量等；不包含槽位序号 | 每个候选的向量 `x_a` |
| Actor | 拼接 `h` 与 `x_a` → 全连接 128 → ReLU → 全连接 1 | 每个合法候选的 logit |
| Critic | `h` → 全连接 128 → ReLU → 全连接 1 | 当前玩家价值 `V(o)`，输出不设 tanh 限幅 |

所有决策阶段共享编码器和动作评分器，通过阶段、动作类型和上下文区分任务。目标参数量约 **20 万～50 万**，不超过 100 万；实际以最终特征维度统计。

同等级市场牌的集合摘要为 `pool_t = Σ_j valid_j × e_card(card_j)`，求和后可除以固定容量 4 控制尺度，并另带有效数量。保留牌按容量 3 缩放；未知保留牌是有效物件，编码其等级和未知标记，不能把它当 padding。三个等级分别聚合，等级差异仍保留。贵族和各方保留区内部同样不依赖排列；自己与对方的集合保持分开。

这里先用非线性网络编码每张牌再聚合，不能只把原始费用相加，否则容易丢失不同卡牌组合的区别。Actor 还要直接读取候选目标的编码，不能只靠全局摘要选择目标。这种共享编码加对称聚合结构来自 Deep Sets 思路，具体宽度是本项目的轻量设计。[Deep Sets 原始论文](https://arxiv.org/abs/1703.06114)

引擎和批处理仍可用数组、内部槽位及动作句柄定位物件，但这些执行用标识不进入网络。交换同等级市场的两张牌，应满足：Critic 的局面价值不变；Actor 给每张具体卡牌对应动作的分数不变，输出只跟着卡牌换位置。不是让两张不同属性的牌得到相同分数，而是让同一张牌摆在哪里都得到同样判断。

策略为 `π(a|o) = softmax(score(h, x_a))`，只在当前合法候选上归一化。批处理时按该批次最大候选数补齐，并屏蔽 padding；不要为所有样本长期存储 252 个候选的稠密副本。训练和推理使用相同的候选与屏蔽规则。[合法动作屏蔽研究](https://arxiv.org/abs/2006.14171)

训练按概率采样；固定评测和人机对局默认选最高分候选，平分时按公开的动作语义或可知目标 ID 作固定处理，不能优先选左边槽位。评测另保留按策略采样的模式，用来检查探索策略与实际部署策略的差距。

### 5.2 与 AlphaZero、随机搜索的区别及扩展路线

| 路线 | 决策及学习方式 | 本项目的取舍 |
|---|---|---|
| 当前 PPO 自我对弈 | 网络直接选择合法动作；根据实际对局回报和价值估计更新策略 | 第一版主线，采样成本较低，先建立可测量的棋力基准 |
| AlphaZero 式流程 | 策略/价值网络引导 MCTS；网络学习搜索访问分布与最终胜负，形成搜索与学习的循环 | 需要反复搜索产生训练目标；用于本游戏还需改造随机事件和隐藏信息处理 |
| 信息集采样搜索 | 采样与当前信息相容的未知牌状态，按真实概率处理补牌，并聚合搜索或模拟结果 | 后续优先比较的推理增强，可复用引擎和已训练网络 |

AlphaZero 的区别不在于“是否自我对弈”或网络大小，而在于使用搜索改进策略，再以搜索结果训练网络；原始流程应用于棋、将棋和围棋这些完全信息游戏。[AlphaZero 原始论文](https://arxiv.org/abs/1712.01815)

本游戏要区分两件事：补牌等随机事件需要机会节点或概率采样；对手的盲保留牌属于隐藏信息，单加机会节点还不够。机会结果按概率抽样或取期望，不能像玩家动作一样选择最有利结果。搜索只能使用玩家信息集与独立采样的假想牌堆，不能从实际引擎复制真实隐藏牌序来预测未来。

后续先比较“小预算信息集采样 + 网络策略 rollout”的动作重评估：一致地分配未知保留牌和剩余牌堆，保证每张牌只出现一次、等级与已知牌一致；模拟双方每次选择时都仅输入各自允许看到的观察。非终局只在根玩家下一次决策点截断，使用该玩家视角的价值估计；终局使用真实模拟结果。先尝试每次决策合计 32～128 条短模拟轨迹，报告实际环境步数、延迟及独立胜率。此范围只是实验预算，不承诺能提升棋力。

若再升级为 ISMCTS，必须维护信息集，避免把每个假想世界中的“知道底牌后最优决策”拼接成现实中无法执行的策略。均匀采样相容隐藏牌只是第一版近似，不代表已经根据对手历史行为求得准确后验。[ISMCTS 原始论文](https://eprints.whiterose.ac.uk/id/eprint/75048/)

搜索增强最先只用于独立推理评测。搜索选出的动作不能直接当作原 PPO 策略采样的动作写回训练；若要训练搜索策略，应单独采用搜索分布蒸馏或经过明确设计的学习流程。已有准确引擎，因此第一版不再学习 MuZero 式世界模型。是否升级搜索由同等墙钟预算下的训练表现、推理速度和棋力决定，不能预先认定 PPO 或搜索必然更强。

## 6. 奖励函数

### 6.1 最终目标：只优化真实胜负

从学习玩家视角定义基础奖励：

| 事件 | 奖励 |
|---|---:|
| 非终局决策 | 0 |
| 按正式结算获胜，包括同分时靠更少已购卡获胜 | +1 |
| 失败 | -1 |
| 最终共享胜利，即双方平局 | 0 |

达到 15 分本身不发胜利奖励，必须等双方回合数补齐后结算。不给拿 token、保留、买牌、取得贵族额外固定正奖励，不设置每步惩罚，避免把囤资源、刷低价卡或缩短对局变成独立目标。

### 6.2 前期辅助：小幅势函数塑形

首轮训练默认在前 **200 万个学习方决策步**使用辅助奖励，之后关闭，最终模型用纯胜负奖励继续训练。这个步数是实验起点，可以依据学习曲线调整。

对学习玩家 `i` 定义：

`Φ_i(o) = 0.7 × tanh((score_i - score_opp) / 15) + 0.3 × tanh((total_bonus_i - total_bonus_opp) / 10)`

`r_train = r_base + α × [γ × Φ_i(o_next) - Φ_i(o)]`

- 初期 `α = 0.1`，后期 `α = 0`；本方案 `γ = 1.0`。
- 真正终局时，后继势函数强制设为 0；工程截断不视为终局，保留正常后继势函数。
- `o_next` 是同一学习玩家的下一个决策观察，可能已经经过对手的完整回合；始终保持同一玩家视角。
- 奖励版本在训练批次和完整对局间切换，不能在一局中途改变 `α`；切换时清空旧 rollout，避免混合目标。

在完整、自然结束的对局中，这种差分形式的辅助奖励会望远镜相消，只留下与初始状态相关的常数，而不会给反复拿取、归还资源累积额外收益。其使用依据是势函数奖励塑形；它不保证 PPO 收敛，也不替代实际胜率验证。[势函数奖励塑形原始论文](https://ai.stanford.edu/~ang/papers/shaping-icml99.pdf)

保留 `α = 0` 的对照实验。如果辅助奖励没有改善独立评测，就直接使用纯胜负奖励。

## 7. 训练方式与流程

### 7.1 先建立可用对手

实现以下策略，它们只能访问自己的观察和合法候选，并且必须覆盖支付、归还和贵族阶段：

| 对手 | 策略方向 | 用途 |
|---|---|---|
| 随机策略 | 每个阶段从合法候选中随机选择 | 引擎压力测试、最低棋力基线 |
| 分数策略 | 偏好可购买的高分牌，缺资源时向得分目标收集 | 测量直接得分能力 |
| 发展策略 | 前期重视低成本加成与贵族进度，后期提高分值权重 | 检查发展与长期规划 |
| 综合策略 | 综合购卡缺口、分值、贵族、黄金保留及对手公开威胁 | 主要固定基线 |

启发式的权重由开发集调试后冻结。它们不是最优策略；评测至少保留两种不同倾向，避免只针对单一漏洞学习。

可以用综合策略产生约 5 万～20 万个决策样本，对 Actor 做 3～5 轮行为克隆热启动。此步骤为可跳过的提速手段；先完成纯 PPO 闭环，再按需要启用，不能把模仿启发式作为训练终点。

### 7.2 单学习方采样，固定对手对弈

**每局只将一个座位作为学习方，开局随机分配先后手；另一个座位使用整局冻结的对手。** 这样先避免双边轨迹混合和价值符号错误。

每轮 PPO 更新遵循：冻结采样策略版本 → 抽取对手并采集 rollout → 计算回报与优势 → 做有限轮次 PPO 更新 → 丢弃旧训练样本 → 开始下一轮。

- rollout 内学习策略不更新，使用其记录的旧 log-probability 和价值；模型快照是对手，不是经验回放数据。
- 对手可以跨采样批次继续一局，但该局内版本始终固定。
- 每个训练样本保存本次观察、候选及有效位、选中候选、旧 log-probability、旧价值、奖励和终止/截断信息。候选可紧凑存储，但更新时必须恢复采样当时完全相同的内容和顺序。
- 保存的是候选和目标物件的原始属性；更新时用当前网络重新计算共享编码，不能把采样时的旧嵌入当成固定输入而切断编码器训练。
- 不将历史模型或启发式产生的行动混入当前学习策略的 PPO 样本。

对手池形成后，默认按以下比例抽取：**50% 本轮采样前的最新模型快照、30% 历史快照、20% 固定启发式对手**。历史池保留 8～16 个版本，兼顾最近版本、过去较强版本和较早的不同风格版本；不要只保留最新一个。

自我对弈不保证每次更新或每个检查点都更强。对当前对手有效的改进，可能牺牲应对其他打法的能力；历史池用于减少这种过度针对和遗忘，不能保证消除它。持续训练使用最新检查点，同时单独保存开发评测最好的检查点用于候选交付，两者不要求是同一个版本。

冷启动时先对随机和启发式对手采样，形成首批模型后逐步切到上述比例。训练中随机牌堆、贵族和先后手；不修改标准规则来制造训练任务。

### 7.3 时间步与 PPO 回报必须定义清楚

训练的一步定义为：**学习方做一次需要选择的决策，环境推进到该学习方下一次需要选择的时刻，或对局结束。**

- 选择购卡目标后，下一个学习步可能是同回合的支付选择。
- 支付后若本回合结束，环境自动执行对手的全部决策，再返回学习方的新观察。
- 对手回合造成的输赢，应计入学习方上一条尚未结束的转移；不能丢失最后的失败奖励。
- GAE 沿同一学习方的决策序列计算。禁止直接把双方交替的观察串起来，用不变的价值符号套用单人 PPO。
- 取 `γ = 1.0`，使终局目标不因胜利早晚或一个真实回合拆成多少子决策而被折扣；GAE 的 `λ` 初值为 0.95。
- 真正终局不 bootstrap。rollout 长度边界和工程超长截断，用该学习方真实后继观察的价值 bootstrap；重置后的新局观察不能代替后继观察，GAE 也不能跨入新对局。

`λ = 0.95` 是初始配置，不是已经验证的最优值；**首轮关键对照包括 `λ ∈ {0.95, 1.0}`，保持 `γ = 1.0`。** 前者更多使用沿途 Critic 估计，通常以一定估计偏差换较小方差；后者在完整自然结束轨迹上更多依赖真实回报。在纯胜负奖励下，完整轨迹的 `λ = 1` 优势为最终胜负减去当前价值基线，但中途截断仍依赖边界价值。[GAE 原始论文](https://arxiv.org/abs/1506.02438)

本游戏的延迟胜负和同回合多个子决策，使 `λ = 1` 特别值得比较；它也会更直接地承受补牌、对手采样和整局结果的方差。`λ = 0.95` 不等于只能学习近处奖励，Critic 能传递长期价值，但初期价值估计不准时会影响早期动作的信用分配。比较时保持同一阶段拆分、奖励及对手方案，记录相同步数的学习曲线和实际耗时，并以多个训练种子的开发评测选取 λ。

训练可设置 **400 个完整玩家回合**的防挂阈值，并在安全的学习方决策边界截断；它不是新游戏规则，不按分数判胜，也不发平局奖励。记录截断比例和回放，若持续偏高，优先检查循环行为、策略和实现。

### 7.4 训练阶段

| 阶段 | 主要工作 | 进入下一阶段的依据 |
|---|---|---|
| 管线验证 | 少量环境跑通采样、更新、保存、恢复和评测 | 无非法动作、NaN、信息泄露；能在简单已知胜负局面上学会正确选择 |
| 初步学习 | 约 20 万～200 万学习方决策步，先学习对抗随机及启发式策略 | 观察独立评测是否进步；明显失败则排查管线，不把某个胜率作为强制切换条件 |
| 主要自我对弈 | 首轮预算 500 万～2000 万学习方决策步，启用历史对手池；累计前 200 万步后关闭塑形 | 对多种启发式和历史版本持续改善 |
| 纯胜负收尾 | 保持纯胜负奖励，继续约 100 万～500 万步或直至平台期 | 纯胜负评测保持或提升，选择验证表现最好的检查点 |
| 独立确认 | 使用最终保留测试集，重复关键实验种子 | 报告棋力、方差、速度和局限 |

上述数字是预算规划，不是训练到某步必然收敛的承诺。默认按预定步数或墙钟预算训练，期间定期保存与评测，预算结束后挑选开发集表现最好的检查点，再做最终独立测试；预算延长须有明确实验理由，不能因为未达到参考胜率而无限训练。简单训练局面必须是规则可达的合法状态，且与最终评测题库分离。

## 8. 4060 Ti 的默认训练配置

CPU 推进游戏和枚举动作，GPU 批量推理与更新。先用 Python + NumPy + PyTorch 实现，训练期间关闭逐步打印和画面渲染，不上分布式训练框架。

| 项目 | 初始设置 |
|---|---|
| 显存预算 | 按 8 GB 设计；争取实测峰值低于 6 GB，给系统显示等留余量 |
| 参数量 | 约 20 万～50 万，上限 100 万 |
| 并行采样 | 先用 4 个 CPU 采样进程、合计 16～32 个逻辑环境，再依据 CPU 实测调整 |
| 每轮 rollout | 合计 8192 个学习方决策样本 |
| minibatch | 512；显存不足或候选较多时降到 256 |
| 每轮 PPO 更新 | 4 epochs |
| 优化器 | Adam，学习率初值 `3e-4`，后期降到 `1e-4` |
| PPO clip / 价值损失权重 | 0.2 / 0.5 |
| 熵奖励系数 | 初值 0.01，后期 0.002；单候选决策不纳入探索统计 |
| 梯度裁剪 / KL 监控 | 最大范数 0.5；目标 KL 初值 0.02，偏离过大时提前结束本轮更新 |
| 精度与内存 | 默认 FP32；rollout 放系统内存，只把当前 minibatch 送 GPU |
| 日志与检查点 | 每轮记关键统计；每 20 万～50 万步进行开发评测并保存可恢复检查点 |

为同一网络版本的请求批量推理，避免多个采样进程各自加载 CUDA 模型并抢占显存。历史模型按需要使用，不必同时全部驻留 GPU。

先做一轮短基准，测量合法动作枚举、环境推进、模型推理、PPO 更新各自耗时，以及 GPU 峰值显存、系统内存和吞吐。只有发现实际瓶颈后，再考虑向量化或加速引擎；小网络不代表 GPU 利用率一定高。

**不预先承诺训练小时数。** 以包含采样和更新的实测“学习方决策步/秒”估算总时长，再另计评测成本。4060 Ti 的模型容量应当足够支撑此规模，但完整训练速度仍取决于 CPU、内存和引擎实现；8 GB 上能完成稳定训练更新是硬件验收条件。

## 9. 测试和棋力评估

### 9.1 引擎与学习接口测试

这些测试落实本地规则契约，不重新判断规则是否正确：

- 覆盖拿取条件、保留上限、有无黄金、所有合法支付、超限归还、贵族选择、牌堆耗尽、先后手终局和全部平局分支。
- 在小规模人工状态上比较完整合法候选集合，尤其检查自愿使用黄金、归还刚拿的 token、多个贵族之间的选择，防止合法动作被遗漏。
- 随机和启发式对局中检查每色 token 守恒、每张牌位置唯一、分数和加成一致、完整回合后的 token 上限。
- 检查同种子同动作可重放、保存恢复结果一致；修改隐藏牌序或对手未知牌，在保持同一已知信息时不改变玩家观察和合法候选。
- 专门构造对手盲保留卡与同等级牌堆中另一张未知牌互换的两种状态：当前玩家的 90 位已购标记、全部观察、候选特征、Actor 概率及 Critic 价值应一致。盲保留动作只改变允许公开的数量等信息，不设置任何已购位。
- 任意重排同等级市场、贵族或各方保留牌，验证价值不变、对应物件动作概率只随物件重排；同时验证动作映射仍买到原来指定的卡。比较使用数值误差容限，并关闭随机采样等干扰。
- 检查训练视角、终局奖励归属、阶段推进、合法候选重建和截断 bootstrap；用明确的一步胜负局面验证价值方向与优势符号。
- 开始长训练前，累计运行至少 1 万局随机/启发式对局，所有正常结束和工程截断均分类记录；不能用静默重开掩盖异常。

### 9.2 评测设计

训练、开发评测、最终测试使用互不重叠的种子集合。最终测试只用于候选模型冻结后的确认，不反复用于调参；固定规则题库也与训练辅助局面分开。

- 每个初始牌堆与贵族配置运行两局，交换候选模型的先后手。只要求初始配置相同，不要求不同策略产生相同后续摸牌历史。
- 开发评测每个关键对手约 200 个种子对，即 400 局；最终评测每个关键对手至少 500 个种子对，即 1000 局。
- 对手同时包括随机、分数、发展、综合策略和多个历史模型。自己对自己只能验证对称性与稳定性，不能证明棋力提升。
- 主指标为 **胜率计分 =（胜局 + 0.5 × 平局）/ 自然结束的有效局数**；并列出胜/平/负、先手和后手成绩，以及总完成率。
- 置信区间按“同种子交换先后手的一对比赛”为重采样单位，避免把关联的两局当作完全独立样本；采用成对 bootstrap 给出 95% 区间。
- 附加指标包括对局长度、最终分差、非法动作/异常/截断比例、推理延迟、显存和训练吞吐。分差只用于分析，不能替代胜率选模。
- 评测超长局保留日志并续跑或调查，不按当前分数强行判胜、也不记平局；存在未解决异常或截断时，该批评测不能用于正式晋级。

### 9.3 正确性验收、棋力参考与模型选择

功能正确性和资源可运行性是硬验收条件；棋力数字是观察学习效果的初期参考，不是训练必须达到的停止条件。冻结评测协议后再开始最终测试：

- **功能门槛：** 完整两人对局可复现；无已知规则错误、非法动作或隐藏信息泄露；模型能加载并完成命令行人机对局。
- **棋力参考：** 对随机策略的胜率计分 95%、对冻结综合启发式 60% 可作为初期参考；实际意义取决于启发式强度，不能预先保证达到。同时报告置信区间及其他对手成绩。
- **模型选择：** 预先固定开发评测对手和权重，按综合胜率计分选择候选；历史池扩展后，入围模型必须在同一对手集合重测才能比较。近似持平时扩大对局数；不只依据击败上一个版本或单个噪声最高点晋级。
- **资源门槛：** 在用户的 4060 Ti 上完成持续采样、训练、检查点恢复与评测，不依赖云端训练。

预算结束后，无论是否达到参考棋力，都如实交付最佳候选、实际曲线、失败对局和可选的下一项实验。达到参考数字也不证明继续训练没有价值；未达到则不能宣称模型已有相应棋力。

候选网络或奖励方案的比较至少使用 3 个训练随机种子。日常调试可以先用单种子缩短反馈时间，最终结论要给出重复实验的波动。

## 10. 后续 agent 的执行顺序与交付物

| 顺序 | 工作包 | 完成标准与交付 |
|---|---|---|
| 1 | 固定两人数据契约、状态与阶段设计 | 简短接口说明，明确完整状态、玩家观察、动作和终局含义 |
| 2 | 实现完整对局引擎与基础回放 | 边界测试、守恒测试、随机对局和保存恢复通过 |
| 3 | 实现基线对手、观察编码和统一评测 | 多种策略能对弈；种子分组、换先手和评测统计可用 |
| 4 | 实现小型模型与 PPO，打通短训练 | 简单胜负局面学习正确；长短回合、终局与截断处理经验证 |
| 5 | 加入对手池，执行主要训练与对照 | 保存训练曲线、资源基准、奖励对照和关键失败回放 |
| 6 | 冻结候选模型，执行独立测试与人机验收 | 最佳模型、恢复点、运行说明、最终评测报告和命令行对局入口 |

每个阶段通过自己的正确性和可运行性检查后再进入下一阶段。长训练前先测吞吐和显存；模型不进步时，检查顺序为：奖励与视角 → 信息和动作完整性 → 基线与对手池 → 采样质量与超参数 → 模型容量。

最终实验报告必须区分“已验证结果”和“待尝试改进”，记录代码/数据/观察动作编码版本、配置、随机种子、训练步数、对手池及硬件实测。恢复训练还需保存优化器、训练计数及随机状态；只保存网络权重不算完整恢复点。

第一版的完成标志是：**本地标准规则下，能稳定运行完整两人对局；小型模型能在 4060 Ti 上训练；独立评测能可靠说明它学到了什么、达到了什么水平。**
